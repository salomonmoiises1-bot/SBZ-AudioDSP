SB — Auditoría integral y optimización de funcionamiento

BASE AUDITADA
- Proyecto: SB / com.sb
- ZIP de entrada: SBZ-AudioDSP-main (4).zip
- Backend real para audio externo: Android AudioEffect/DynamicsProcessing sobre sesión global 0.
- El proyecto no recibe PCM de otras aplicaciones; PcmAudioPipeline queda reservado para consumidores que entreguen PCM directamente.
- API objetivo: Android 14 / compileSdk 34 / minSdk 28.
- Workflow de CI: Gradle 8.5 + JDK 17.

TRAZADO AUDITADO
UI
 -> MainViewModel
 -> DspConfig.validate()
 -> DspEngine.updateConfig()
 -> coalescing de configuración
 -> DynamicsProcessingManager / fallback EqualizerManager
 -> BassBoostManager + VirtualizerManager
 -> AudioMeterManager / Visualizer para medición RMS

PERSISTENCIA
UI -> debounce 180 ms -> PresetRepository/DataStore.
La restauración inicial ahora ocurre en SbAudioService antes de crear los efectos.

HALLAZGOS Y CORRECCIONES

1. Carrera de arranque de configuración — CORREGIDA
Antes, SbApplication y SbAudioService podían restaurar/usar la configuración en paralelo y el servicio podía crear el backend con DEFAULT antes de recibir el estado persistido.
Ahora el servicio restaura DataStore primero y recién después inicia el backend global. Las acciones START/TOGGLE esperan a que ese arranque esté listo.

2. Carrera entre configuración y ciclo de vida del DSP — CORREGIDA
El coalescer del DspEngine podía intentar aplicar una configuración mientras start/recover/stop estaba creando o liberando efectos.
Ahora las aplicaciones coalescidas se serializan mediante el mismo Mutex del ciclo de vida.

3. AutoGain no seguía continuamente la medición RMS — CORREGIDO
La medición se actualizaba periódicamente, pero la ganancia efectiva sólo se aplicaba cuando cambiaba la configuración.
Ahora AutoGain recalcula su corrección durante el ciclo de medición y modifica únicamente la ganancia de entrada cuando cambia de forma significativa. No reescribe EQ/MDRC/limiter en cada medición.

4. Escrituras innecesarias de DynamicsProcessing — OPTIMIZADAS
DynamicsProcessingManager ahora diferencia cambios de:
- EQ/Tone
- MDRC/crossovers
- Limiter
- ganancias de entrada
Un movimiento de Master/Balance/AutoGain no provoca una reescritura completa de EQ/MDRC/limiter.
Los cambios de EQ siguen usando coalescing en HandlerThread.

5. Seguridad del escritor de EQ frente a release/recovery — CORREGIDA
La escritura asíncrona del EQ y la liberación/reconstrucción de DynamicsProcessing ahora están sincronizadas para evitar que el worker escriba sobre una instancia que está siendo liberada.

6. BassBoost/Virtualizer — OPTIMIZADOS
Se evita repetir setStrength y readback del driver cuando el valor no cambió.
El efecto sigue siendo habilitado/deshabilitado según DspConfig.

7. Fallback Equalizer — OPTIMIZADO
Cuando DynamicsProcessing no está disponible, el Equalizer nativo sólo reescribe sus bandas cuando la configuración efectiva cambió.

8. MDRC externo — VALIDADO
Los crossovers se actualizan mediante setters de las bandas MBC existentes; no se reconstruye DynamicsProcessing por mover un crossover.
Los límites lógicos se mantienen en 20–22000 Hz y los cuatro cortes permanecen estrictamente ascendentes mediante DspConfig.validate().

9. Gain Reduction — CORREGIDO PARA NO ENGAÑAR
DynamicsProcessing no expone al cliente la reducción interna del MBC. Se eliminó el estado/medidor que podía mostrar cero como si fuese una lectura real del hardware.
MdrcProcessor continúa disponible exclusivamente para la ruta PCM directa que sí procesa muestras.

10. Ruta PCM directa — OPTIMIZADA
PcmAudioPipeline no se conecta artificialmente al audio de otras aplicaciones.
processInterleaved() reutiliza buffers en lugar de crear dos FloatArray por llamada.
Los parámetros estructurales de Bass Boost, Tone, EQ y MDRC sólo se recalculan cuando cambian.

11. EQ lógico — CONSERVADO
DspConfig mantiene exactamente EQ10/EQ20/EQ32 y las 32 frecuencias lógicas de EQ32.
DynamicsProcessing proyecta las bandas lógicas sobre el número físico que el HAL acepta. No se confunde el modelo lógico con la cantidad física real de filtros.

12. Orden y limitaciones del backend externo
La API pública de DynamicsProcessing permite controlar directamente Pre-EQ, MBC, limiter y ganancias de entrada, pero no ofrece un Master Gain/Balance posterior al limiter ni permite a SB imponer el orden global entre efectos independientes como BassBoost/Virtualizer.
Por eso esos controles se aplican en los puntos que la API realmente permite. No se simula una ruta PCM inexistente.

13. Watchdog
El watchdog continúa verificando la salud del backend real y puede recuperar la instancia si Android/vendor invalida el efecto.
Los estados de inicialización del motor relevantes para el watchdog están marcados como visibles entre hilos.

VALIDACIÓN ESTÁTICA
- Kotlin del proyecto revisado: sin desbalance básico de llaves/paréntesis.
- No quedaron referencias al estado eliminado de Gain Reduction.
- No se encontró la referencia prohibida en el código/documentación auditados.
- Se conserva el workflow que instala Gradle 8.5 directamente en GitHub Actions.

VALIDACIÓN DE COMPILACIÓN
El entorno local disponible no tiene Gradle instalado y el ZIP no contiene gradle-wrapper.jar ejecutable localmente. Por ello no se afirma una compilación local.
La validación definitiva debe hacerse mediante GitHub Actions con:
1. gradle test --stacktrace
2. gradle assembleRelease --stacktrace
3. verificación de release-output/SB.apk

RESULTADO
La optimización se concentra en el camino real de audio externo: menos escrituras al HAL, actualizaciones serializadas, AutoGain funcional durante la reproducción, restauración determinista de configuración y eliminación de indicadores que no podían representar mediciones reales.
